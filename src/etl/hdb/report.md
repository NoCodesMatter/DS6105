# HDB Data Preparation and Validation

SD6103 Data Systems Group Project

Task 2 contribution by HE RUOYUN

## 1 Data sources and acquisition

The HDB data preparation component converts the five prescribed resale datasets into relational data for analysing resale prices, flat attributes and lease duration. A Python pipeline acquires and profiles the original files, applies a common set of transformations, and produces `town.csv`, `hdb_building.csv`, `hdb_flat.csv` and `resale_transaction.csv`. These outputs implement the HDB portion of the shared schema, version `1.0.0-draft.2`, and provide the building identities used by the spatial component.

The source is the HDB resale price collection on data.gov.sg [1]. All five files were acquired on 18 October 2026. The frozen snapshot contains 989,158 transactions, with observed months from January 1990 to October 2026. The acquisition manifest records each dataset identifier, source URL, acquisition time, file size and SHA-256 checksum [2]. Keeping this snapshot fixed gives all database stages the same source data, including a consistent version of the regularly updated 2017 onwards file.

Table 1 summarises the source files. The 2015–2016 file was selected for the initial population because it is the smallest, allowing the transformation and import process to be checked on 37,153 records before processing the larger combined dataset.

## 2 Transformation into relational tables

### 2.1 Entity extraction and record identity

The pipeline extracts towns, buildings and flat profiles from the transaction records. A building is identified by its canonical block and street name and references one town. A flat profile combines its building, flat type, lower and upper storeys, floor area, flat model and lease commencement year. The source describes flats at this attribute level without a unit number, so the resulting entity represents an observed profile. Multiple transactions can reference the same profile.

Building and flat identifiers are deterministic UUIDv5 values generated by the shared identity functions. Rebuilding the same canonical entities therefore produces the same identifiers, supporting joins between the HDB and spatial outputs. Each transaction is identified separately by its source dataset and original one-based CSV record ordinal. This preserves every observed sale, including records whose published attributes are identical. CSV parsing determines record ordinals, so a quoted field containing a line break remains part of one record.

### 2.2 Text dates and numeric values

Text fields undergo Unicode NFKC normalisation, conversion to uppercase, trimming and whitespace consolidation. The historical flat type `MULTI-GENERATION` is mapped to `MULTI GENERATION`. Address punctuation and abbreviations are retained to preserve the shared address convention. Storey ranges such as `04 TO 06` become integer lower and upper bounds; the original interval widths remain intact. This retains the information supplied by historical files with different storey groupings.

The source month is represented as a PostgreSQL date on the first day of that month. The day is a storage marker for monthly data. The source uses approval month through February 2012 and registration month from March 2012. Floor area and resale price are parsed with decimal arithmetic and written to two decimal places after precision and range checks. This maintains exact numeric values during conversion to PostgreSQL numeric columns. Building latitude and longitude are initially exported as a paired SQL NULL for subsequent geocoding.

### 2.3 Remaining lease harmonisation

The files contain three lease representations. Reported whole years are multiplied by 12 and labelled `reported_years`. Text containing years and months is converted to total months and labelled `reported_months`. For the three older files without a remaining lease column, the pipeline applies the shared 99-year lease assumption: remaining months = 12 × (99 − (sale year − lease commencement year)). These estimates are labelled `estimated_years`. Retaining the basis alongside the value preserves the distinction between year-resolution estimates and source-reported values.

An estimate outside the valid range of 0 to 1,188 months is stored as SQL NULL with `lease_basis=unknown`, while the transaction and its original lease commencement year are retained. Across the full snapshot, 708,999 transactions have estimated leases, 37,153 have reported whole-year leases, 242,955 have reported month-resolution leases and 51 have unknown leases [3, 4].

## 3 Data quality findings and their treatment

Profiling examined every record in all five sources. The snapshot contains no blank source fields and no fatal normalisation errors. It contains 1,929 additional occurrences of identical source records, including 24 in the initial 2015–2016 file [3]. As the published attributes do not uniquely identify a dwelling or sale event, these occurrences are retained with distinct transaction identifiers. Entity deduplication is applied to towns, buildings and flat profiles, while transaction counts remain equal to the original source counts.

The 10,024 canonical building addresses each map to a single town. Three addresses have multiple lease commencement years: block 114 JURONG EAST ST 13 has 1981 and 1982; block 21 TEBAN GDNS RD has 1978 and 2013; and block 37 TEBAN GDNS RD has 1966 and 1981. These observations support retaining lease commencement year in the flat profile. Moving it to the building would collapse distinct observed values. The profiling output records the original source rows for each case, connecting this modelling decision to the data.

Another 51 transactions have a sale year earlier than their recorded lease commencement year: 36 in the 1990–1999 file and 15 in the 2000–February 2012 file. Applying the historical estimate would produce a remaining lease above 99 years. These records receive an unknown remaining lease and keep their source attributes for analysis. The diagnostics contain two events per affected record, covering the pre-commencement sale and the out-of-range estimate. Thus 102 diagnostic entries describe 51 transactions, approximately 0.0052% of the snapshot.

## 4 PostgreSQL population and validation results

The generated CSVs were loaded into PostgreSQL 15.19 using the shared schema and its existing constraints. The four tables were imported in dependency order: town, building, flat profile and transaction. Explicit column lists define the mapping from each CSV to its table. All four imports run within one database transaction, providing an atomic population step.

Two completed database validations cover the initial file and the full five-file snapshot. Table 2 reports the populated table sizes [4]. Both imports preserved every source transaction. SQL checks found zero duplicate primary or natural keys, orphan foreign keys, invalid prices, invalid month markers or violations of the implemented lease rules. The 51 unknown lease values in the full snapshot were confirmed as SQL NULL.

**Table 2 Verified PostgreSQL table counts**

| Table | Initial 2015–2016 file | All five sources |
|---|---:|---:|
| `town` | 26 | 27 |
| `hdb_building` | 7,921 | 10,024 |
| `hdb_flat` | 28,725 | 147,045 |
| `resale_transaction` | 37,153 | 989,158 |

Validation also exported each populated table and compared every field with the corresponding CSV record, matched by primary key. All comparisons passed, establishing that the imports preserved dates, text, identifiers and decimal values as well as row counts. Thirteen deliberately invalid operations per database tested constraint enforcement, including duplicate keys, missing parent references, invalid dates, numeric overflow and inconsistent lease values. Each produced its expected PostgreSQL error code. A separate invalid final-table import caused all four table loads to roll back, confirming the atomic loading behaviour. The accompanying regression suite recorded 53 passing tests [4].

## 5 Implementation issues and reproducibility

The main data preparation issues were differences in lease representation, historical text conventions and the distinction between repeated attributes and transaction identity. Handling these explicitly made the same transformation code applicable to all five files. Validation on the three-source combination of March 2012–December 2014, 2015–2016 and 2017 onwards processed 332,311 transactions and exercised all three lease representations. The full five-source import then exercised the historical unknown-lease cases.

Implementation review also identified two portability issues. Git line-ending conversion could change a source-code checksum between Windows and Unix checkouts, so code provenance now hashes UTF-8 text with normalised LF line endings. Raw data and generated CSVs retain byte-exact checksums. During PostgreSQL verification, temporary SQLite connections used for comparison had to be explicitly closed so Windows could remove their temporary files. These changes improved reproducibility and cleanup while preserving the data and schema.

Each successful run produces four table CSVs, a diagnostics file and a manifest containing source and output checksums, transformation counts and source-to-output reconciliation. Outputs are prepared in a staging directory and published after successful transformation. Repeating the initial build produced identical SHA-256 checksums for all four table CSVs and the diagnostics file [5]. The source-selection parameter supports cumulative database stages by rebuilding the selected combination with the same identity and transformation rules. The frozen inputs are distributed through the project release, and the executable acquisition, transformation and verification commands are documented with the module [6]. Together, these outputs provide a reproducible HDB data layer for spatial integration and the subsequent query experiments.
